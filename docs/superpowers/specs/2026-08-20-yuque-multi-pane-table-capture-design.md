# 语雀多窗格表格采集重构设计

## 背景

v2 首版假设语雀“表格视图”在一个 `<table>` 内同时暴露表头和完整记录行。真实企业语雀页面并不满足这个假设：同一个逻辑表格由多个独立 DOM 窗格共同渲染，固定列、可滚动字段和分组区域可能分别使用不同的 `<table>` 或行容器。

现场匿名诊断已经确认：

- 当前页面可见 34 个行节点。
- 主窗格的数据行结构为 `tr > td[role=button] > div`。
- 每个主窗格行只暴露一个逻辑字段，而不是整条记录的全部字段。
- 因此只调用 `document.querySelector('table')` 必然只能取得一个窗格，无法生成完整记录。

此前对原生 `button`、`role="button"` 和标准 `<tr>` 的兼容只能改变单个窗格内的解析方式，不能解决跨窗格合并问题。本次重构改为先发现逻辑网格布局，再按视觉行列关系合并多个窗格。

## 目标与范围

本次重构继续支持当前打开的单篇语雀表格或看板：

- 从看板临时切换到已有的“表格视图”。
- 采集表格视图当前筛选、分组和排序后的记录。
- 合并固定列与滚动列，生成字段顺序正确的 Markdown 和 CSV。
- 保留普通文档 v1 导出能力。
- 全部内容仅在当前浏览器本地处理。

本次不包含：

- 读取或破解语雀加密接口。
- 批量导出多个文档或知识库。
- 自动清除筛选条件。
- 在无法证明行列对齐时生成可能错位的文件。

## 方案比较

### 方案 A：按视觉几何关系合并多个 DOM 窗格（采用）

枚举当前表格视图中的所有表格和行容器，通过元素的可见矩形识别表头列、记录行和单元格。相同纵向位置的单元格属于同一条记录，相同横向区间的单元格属于同一字段。

优点：不依赖某一个固定的标签嵌套；可以同时处理固定列、独立表格窗格和普通单表；与用户实际看到的布局一致。缺点：需要容差、可见性和滚动同步校验，测试量比单表选择器更大。

### 方案 B：为当前语雀 DOM 编写多个专用选择器

分别识别固定列和滚动列的类名或层级，再按 DOM 顺序合并。

优点：当前页面实现较快。缺点：类名和层级是语雀私有实现，升级后容易再次失效；当前证据仍不足以覆盖所有窗格变体。不采用。

### 方案 C：拦截内部接口或解密状态

从语雀前端内部状态获得完整数据。

优点：理论上不需要滚动。缺点：强依赖私有实现，并引入安全和维护风险；与本插件“不读取凭证、不破解密文”的边界冲突。不采用。

## 架构

### 1. 布局发现层

`lib/table-page.js` 中新增独立的布局发现函数，输入当前 `document`，输出不含业务内容的布局描述：

```js
{
  columns: [
    { id: "column-0", name: "待办事项", left: 308, right: 890 }
  ],
  rowBands: [
    { top: 286, bottom: 325, sources: [/* DOM elements */] }
  ],
  panes: [
    { element, rect, rows, verticalScroller, horizontalScroller }
  ]
}
```

发现规则：

- 枚举活动表格视图内所有可见 `<table>`、`[role=grid]`、`[role=row]` 和可交互单元格。
- 使用 `getBoundingClientRect()` 排除隐藏、零尺寸和不在表格区域的节点。
- 表头字段按横向位置排序；同一横向区间的重复表头去重。
- 数据行按 `top/bottom` 聚类，允许少量像素误差，避免不同窗格的同一视觉行被拆开。
- 分组标题、统计行和“添加记录”没有完整字段覆盖，不进入记录行集合。
- 布局发现不读取 Cookie、Local Storage、Token 或网络响应。

### 2. 窗格采样层

每次采样只处理当前已渲染区域：

1. 重新计算可见行带，避免虚拟滚动复用旧 DOM 节点。
2. 收集所有与行带纵向重叠的可见单元格。
3. 依据单元格横向中心点落入的字段区间写入对应字段。
4. 一个字段出现多个嵌套文本节点时，只读取最外层语义单元格，避免重复文本。
5. 空字段保留空字符串；链接、多选和人员继续沿用现有规范化逻辑。

记录标识按以下优先级生成：

1. 页面暴露的 `aria-rowindex`、虚拟索引或稳定 `data-*` 行标识。
2. 主字段文本、当前分组和同名记录出现序号组成的稳定键。
3. 如果无法区分重复主字段且没有稳定索引，则采集失败，不静默合并或覆盖。

### 3. 虚拟滚动与横向字段

- 发现所有窗格的滚动容器并记录原始位置。
- 纵向滚动以主记录窗格为驱动；每次移动后等待两帧和短暂稳定时间，再重新发现布局。
- 如果字段被水平虚拟化，则分段横向滚动并按记录键合并字段。
- 每个滚动位置都校验多个窗格的可见行带是否一致；不一致时等待重试，持续不一致则失败。
- 到达底部且连续三轮没有新增记录后才结束。
- 在 `finally` 中恢复全部滚动位置和原始看板/表格视图。

### 4. 完整性保护

只有同时满足以下条件才允许输出：

- 至少发现一个字段和一条记录。
- 所有记录均能生成稳定键。
- 同一记录在不同采样批次中的已知字段没有冲突。
- 所有必需窗格完成纵向遍历；存在横向虚拟化时也完成横向遍历。
- 已到达底部并通过三轮稳定检查。

任何无法解释的行错位、重复键冲突或窗格不同步都会抛出编码错误，并且不生成文件。

## 本地诊断与弹窗 UI

诊断信息不再拼接进错误正文。

- 弹窗宽度固定为 360px，所有 Grid/Flex 子项设置 `min-width: 0`，长文本使用 `overflow-wrap: anywhere`。
- 错误区只显示简短的人类可读提示，例如“未读取到可导出的表格记录”。
- 存在布局诊断时显示折叠的“诊断信息”区域，默认关闭。
- 区域内提供“复制诊断信息”按钮，复制匿名结构供开发排查。
- 匿名诊断覆盖全部表格窗格，只包含标签、ARIA 角色、子节点形状、文本类型、行列数量和几何尺寸，不包含事项、人名、链接或其他业务文本。

错误传递契约调整为：

```js
{
  ok: false,
  error: {
    code: "NO_RECORDS",
    message: "未读取到可导出的表格记录",
    details: { diagnostic: "tables=..." }
  }
}
```

## 文件调整

- `popup/popup.js`：渲染、隐藏和复制诊断信息。

- Manifest 与权限不变。

## 测试策略

所有生产修改继续使用红—绿—重构循环。

自动化测试至少覆盖：

- 单表结构仍能导出，防止已有兼容回退。
- 固定主列与两个独立字段窗格按视觉行位置正确合并。
- 不同窗格存在 1–2 像素偏差时仍属于同一行。
- 分组标题不被当作记录。
- 空字段不会造成后续字段左移。
- 重复主字段在有稳定索引时分别保留；无稳定标识时安全失败。
- 虚拟滚动后 DOM 节点复用不会覆盖旧记录。
- 窗格不同步、字段冲突和超时不会生成残缺结果。
- 错误正文简短，匿名诊断独立传递。
- 弹窗样式包含固定宽度和长文本换行约束。
- 普通语雀文档、Markdown、CSV 和图片本地化全量回归。

## 验收标准

1. 弹窗触发错误后仍保持 360px，不再横向扩张。
2. 诊断默认折叠，点击后可复制完整匿名信息。
3. 当前企业语雀表格可以导出 Markdown 和 CSV。
4. 导出字段顺序与表格视图一致，空字段、人员、多选和链接不串列。
5. 导出记录数与当前筛选后的表格记录一致。
6. 看板触发导出后能恢复原视图和滚动位置。
7. 普通文档 v1 功能无回归。

## 实施顺序

1. 先完成错误详情契约和固定宽度诊断 UI，用真实页面收集全部窗格的匿名布局证据。
2. 根据该证据建立多窗格 DOM 测试夹具。
3. 实现布局发现与几何行列合并。
4. 接入虚拟滚动和完整性校验。
5. 完成全量自动化测试与真实 Chrome 验收。
